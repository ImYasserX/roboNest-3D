# RoboNest.3D

Bilingual (Iraqi Arabic / English) e‑commerce platform for **RoboNest.3D**, the 3D‑printing workshop of RoboNest. RoboNest.3D designs and prints its own products: made‑to‑order prints, customizable products and downloadable 3D models, plus custom print jobs from customer files. Payments are arranged with the team on WhatsApp (physical items can also be paid in cash on delivery) and count only after an Owner verifies them in the admin; a flat 5,000 IQD delivery fee applies everywhere, and orders above 50,000 IQD need a 30% deposit first ([docs/PAYMENTS.md](docs/PAYMENTS.md)). (This is not the international RoboNest electronics store.)

- **Stack:** Next.js 16 (App Router, TypeScript), Tailwind CSS 4, next‑intl, Drizzle ORM, Zod.
- **Runtime:** Cloudflare Workers via OpenNext, with Cloudflare D1 (SQLite) and R2 (object storage).
- **Status:** built and verified locally. **Not deployed.** See [`FINAL_AUDIT.md`](FINAL_AUDIT.md) for what was verified and what must happen before launch.

## Requirements

- Node.js ≥ 20.18 (developed on Node 24) and npm
- No Cloudflare account is needed for local development: Wrangler runs D1 and R2 locally (Miniflare/workerd).

## Local development

Full guide, local resource locations, the outbound kill switch and a repeatable smoke test: [docs/LOCAL_DEVELOPMENT.md](docs/LOCAL_DEVELOPMENT.md). No domain or Cloudflare account is needed.

```bash
npm install
npm run setup            # creates .dev.vars with a random APP_SECRET, applies D1 migrations locally
npm run db:seed          # sample catalog, 19 delivery locations, 2 dev admin accounts (passwords printed once)
npm run dev              # http://localhost:3000  → redirects to /ar (or /en by browser language)
```

- Storefront: `/ar`, `/en`. Admin: `/ar/admin`, `/en/admin`.
- The seed prints the passwords for the development accounts `dev-super` (Super Admin) and `dev-ops` (Operations). They are not the real owners. To choose them yourself, set `SEED_SUPER_ADMIN_PASSWORD` and `SEED_OPS_ADMIN_PASSWORD`. The Super Admin must enroll an authenticator app (TOTP) at first sign‑in.
- `npm run db:seed -- --reset` wipes local D1/R2 and reseeds. Seed products are clearly marked samples; their images are rendered from procedural 3D meshes, the sample STL downloads use the same geometry, and the interactive previews are separate reduced proxies generated from it and approved by the seed. The seed creates no orders, customers, or reviews.
- Discount code for local testing: `WELCOME10`.

### Running the production bundle locally

```bash
npm run cf:build                               # next build + OpenNext → .open-next/ (+ bundle secret check)
npx wrangler dev --port 8787 --ip 127.0.0.1    # runs the Worker in workerd with local D1/R2
```

Use `http://localhost:8787` (not 127.0.0.1): production cookies are `__Host-`/`Secure`, which browsers accept on `localhost` only.

## Environment

All variables are listed with comments in [`.env.example`](.env.example) (no real values).

> **Build safety.** OpenNext copies values from `.env`, `.env.local` and `.env.production*` into the Worker bundle. Built Workers ignore them (bindings only), and `npm run cf:build` **fails** if a secret such as `RESEND_API_KEY` ended up in the bundle. Keep real secrets in `.dev.vars` locally and in Worker secrets in production, not in `.env*` files on the machine that builds for deployment. For a local-only test bundle you can run `CF_BUILD_ALLOW_ENV_SECRETS=1 npm run cf:build`; never deploy such a build.
 Local values live in `.dev.vars` (generated by `npm run setup`, git‑ignored); under `next dev`, `.env.local` is also read as a fallback by `getServerVar()` (`src/server/env.ts`). In production, set secrets with `npx wrangler secret put NAME` and non-secret values in `wrangler.jsonc` `vars`. Secrets are only read on the server, never use `NEXT_PUBLIC_`, and the admin shows only whether each one is set. Missing configuration is logged once per isolate by variable **name** only.

| Name | Kind | Purpose |
|---|---|---|
| `DB`, `MEDIA`, `PRIVATE_FILES`, `IMAGES` | bindings | D1 database and R2 buckets (`wrangler.jsonc`) |
| `APP_SECRET` | secret, required | ≥ 32 chars. Encrypts admin TOTP secrets, derives order link tokens, HMACs WhatsApp OTP codes and IPs |
| `SITE_URL` | var, required | Public https origin; used for canonical URLs and admin links in Telegram |
| `RESEND_API_KEY` | secret | Resend API key |
| `CONTACT_FORM_EMAIL` | var | Contact-form recipient. Set to `contact@robonest.tech` in `wrangler.jsonc` |
| `CONTACT_FROM_EMAIL` | secret/var | Separate sender on a Resend-verified domain, e.g. `RoboNest.3D <no-reply@robonest.tech>` |
| `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_IDS` | secrets | Owner order alerts (both owners' chat ids, comma-separated) |
| `TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_TOKEN`, `TWILIO_VERIFY_SERVICE_SID` | secrets | SMS phone verification (default channel) |
| `PHONE_VERIFICATION_PRIMARY`, `WHATSAPP_*` | secrets/vars | Optional WhatsApp OTP channel under evaluation ([docs/WHATSAPP_OTP.md](docs/WHATSAPP_OTP.md)) |
| `FIB_*` | (retired) | Ignored: automatic FIB payments were retired on 2026-10-12 ([docs/PAYMENTS.md](docs/PAYMENTS.md)) |
| `OUTBOUND_INTEGRATIONS` | var | `disabled` hides all provider credentials so nothing is sent. Always set by E2E and Vitest; optional for quiet local work ([docs/LOCAL_DEVELOPMENT.md](docs/LOCAL_DEVELOPMENT.md)) |
| `NEXT_PUBLIC_IMAGE_TRANSFORMS` | build var | `cloudflare` in production builds |
| `SEED_*` | local only | Seed inputs for development and E2E; never against production |

### Contact form (Resend)

- Recipient: `CONTACT_FORM_EMAIL` = `contact@robonest.tech` (in `wrangler.jsonc`).
- Sender: `CONTACT_FROM_EMAIL`, a different address on a domain you verified in Resend (Resend → Domains, DNS records added and status "Verified"). The app validates the format but cannot see Resend's verification status; Resend rejects unverified senders, and the form then reports a failure.
- The sender must differ from the recipient; the app refuses to send otherwise.
- `npm run email:check` checks the variables, the public DNS records and (if the key may) Resend's domain status, and sends nothing. `npm run email:test -- --to <your inbox>` sends exactly one test email after you type `SEND`.
- Admin → Settings → **Contact form email** lists configuration problems by name and has **Send test email**, which reports Resend's real answer.
- Visitors see "sent" only when Resend accepted the email (HTTP 2xx with an email id). Every submission is also stored in D1 (admin → Messages) with its delivery status.

### Telegram order alerts

1. **Create the bot.** In Telegram, open **@BotFather** (blue check mark), send `/newbot`, choose a name (e.g. "RoboNest.3D Orders") and a username ending in `bot`. BotFather replies with the token (`123456789:AA…`). Treat it like a password: never paste it in chats, issues, screenshots or the browser address bar.
2. **Both owners start the bot.** Each owner opens `https://t.me/<bot_username>` on their own Telegram account and presses **Start** (a bot cannot message someone who never started it).
3. **Get the chat ids without exposing the token.** On your own computer, put the token in `.dev.vars` as `TELEGRAM_BOT_TOKEN=…` (git-ignored) and run `node scripts/telegram-chat-ids.mjs`. It prints the bot's name and the id, name and @username of every private chat that started the bot, and a ready `TELEGRAM_CHAT_IDS=…` line. It never prints the token. If no chats appear, ask the owners to send the bot any message and run it again (Telegram keeps these updates for about 24 hours).
4. **Set the Worker secrets** (production): `npx wrangler secret put TELEGRAM_BOT_TOKEN` and `npx wrangler secret put TELEGRAM_CHAT_IDS` (value like `111111111,222222222`). Wrangler prompts for the value, so it is not stored in shell history.
5. **Test without touching any data.** `npm run telegram:check` verifies the token and that each chat id is reachable, **sending nothing**. `npm run telegram:test` sends a fixed "NOT an order" message to each chat. Both read `TELEGRAM_BOT_TOKEN` / `TELEGRAM_CHAT_IDS` from the environment or `.dev.vars` (or prompt for the token, hidden), talk to Telegram directly, and never use the app database or Cloudflare. Admin → **Notifications → Send test message** tests the deployed Worker's own secrets; it records a TEST notification row and an audit entry (no order data). Each owner must confirm they received the message.

Keep the token in `.dev.vars` (local) and Worker secrets (production), **not** in `.env.local`: `.env*` values get copied into build bundles, and `npm run cf:build` refuses such a build.

**Troubleshooting** (the admin shows a hint next to each error): `401 Unauthorized`: the token is wrong or was revoked; issue a new one with BotFather `/token`. `403 Forbidden: bot was blocked by the user` or `can't initiate conversation`: that owner has not pressed Start or blocked the bot. `400 Bad Request: chat not found`: wrong chat id; re-run the script. `429`: Telegram rate limit, retried automatically. Network/timeout: retried automatically with backoff. Orders are never affected: alerts sit in the outbox and are retried; permanent errors wait for **Retry** after you fix the cause.

### Phone verification

Twilio Verify SMS is the default and stays enabled. WhatsApp (Meta Cloud API) is implemented behind the same interface for evaluation, with "send by SMS instead" as the fallback; see [docs/WHATSAPP_OTP.md](docs/WHATSAPP_OTP.md). Twilio setup: create a Verify service, enable SMS, set the three `TWILIO_*` secrets, and register an alphanumeric sender for Iraq (Asiacell requires registration from July 2026).

### Owner accounts

See [docs/PRODUCTION_SETUP.md](docs/PRODUCTION_SETUP.md), step 7. In short: each owner runs `npm run owner:bootstrap -- yasser|ayman`, applies the generated SQL with Wrangler, deletes the file, and enrolls TOTP at first sign-in.

## Database migrations

Schema: `src/server/db/schema.ts`. Migrations: `drizzle/migrations/`, applied by Wrangler.

```bash
# after changing schema.ts
npm run db:generate                 # drizzle-kit → new SQL migration file (review it!)
npm run db:migrate:local            # apply to local D1
npx wrangler d1 migrations apply robonest-3d --remote   # production (see deployment checklist)
```

Never change the production schema by hand. Every change goes through a reviewed migration file.

```
e2e/                      Playwright
```
